from a retrieved corpus — or an explicit refusal when the corpus doesn't support one.

## 4. Architecture

```
Browser (Next.js, Vercel)
  │  push-to-talk mic → AudioWorklet resamples to 16kHz mono PCM16
  │  WebSocket: wss://<backend>/ws/transcribe?language=..&strategy=..
  ▼
FastAPI backend (Railway, Docker)
  │
  ├─ SarvamSTTClient ──ws──▶ Sarvam Saaras v3 realtime STT
  │    (server-side only — SARVAM_API_KEY never reaches the browser)
  │    partial transcripts ──▶ speculative retrieval (background thread)
  │    final transcript ──▶ pipeline (reuses speculative hit if it resolved in time)
  │
  ▼ [MEASURED WINDOW — spec §13.1]
  1. Input guardrails       (script/pattern checks, ~1ms)
  2. Encode + retrieve      (e5-small ONNX encode, FAISS dense + BM25 sparse, RRF fusion)
  3. Retrieval-confidence gate  (tau_abs / tau_margin, calibrated — spec §11.2)
  4. Generate                (Groq primary / Cerebras failover, circuit breaker)
  5. Grounding verification  (mDeBERTa-v3 XNLI entailment, toggleable)
  ▼
Answer + citations + per-stage timings → WebSocket → browser
```

**Request trace for one voice query:**

1. Browser opens `/ws/transcribe`; server opens its own WS to Sarvam and bridges audio.
2. Sarvam emits `transcript.partial` events as the user speaks. Each one past a
   3-token floor fires `retriever.retrieve()` in a background thread, cached by an
   exact hash of the partial text (`app/stt/speculative.py`).
3. Sarvam emits `transcript.final`. If it exactly matches the last partial that
   already resolved, the pipeline reuses that cached retrieval — the retrieve stage
   reports near-zero latency, honestly (not omitted).
4. `run_pipeline()` (`app/pipeline.py`) runs input guardrails → retrieval (or the
   cache hit) → confidence gate → generation → grounding, recording
   `time.perf_counter()` durations at every stage into a typed `StageTimings` object.
5. Every outcome is logged as one structured JSON line: request id, transcript,
   language, stage timings, scores, refusal reason, provider used, retries.
6. The final `PipelineResponse` (answer, cited chunks with scores, refusal reason if
   any, per-stage timings) goes back over the same WebSocket.

**Deployment topology:** frontend on Vercel (static/client-only, no server actions in
the request path); backend on Railway (Docker, not Hugging Face Spaces — see
[Limitations](#9-honest-limitations)); corpus + built indexes on a Hugging Face
dataset repo, pulled at container startup (`app/artifacts.py`) since container disk on
both platforms is ephemeral.

**Explicitly rejected** (per spec §4): hosted embedding APIs, hosted vector DBs,
cross-encoder rerankers, LLM-as-judge guardrails, TTS output.

## 5. Guardrails

Three layers, all individually toggleable (`config/default.yaml`'s
`guardrails.enable_*` flags) so ablations can be run.

**Input guardrails** (~1ms budget): empty/too-short transcript, curated unsafe/prompt-
injection pattern lists (`app/guardrails/injection.py`, `safety.py` — English-focused;
a documented gap for the other 13 languages, see Limitations), script-based language
identification reusing the corpus's own quality-gate logic
(`app/data/languages.py::script_fraction`).

**Retrieval-confidence gate** (0ms — reuses scores retrieval already computed):
abstains when the top-1 fused score is below `tau_abs`, **or** the margin between
top-1 and the mean of ranks 2–5 is below `tau_margin`. The margin test is the
important one: a flat threshold is a guess, a low margin is the actual signature of
"many mediocre matches" — i.e. an off-topic query. Both thresholds are calibrated, not
hand-picked, by `scripts/calibrate_guardrails.py` against the eval set's answerable
queries vs. a held-out "corpus-excluded" bucket (spec §5/§11.4) plus a small
hand-authored off-topic sample.

**Grounding verification** (measured ~420ms, PyTorch fp32 — see Limitations):
mDeBERTa-v3 XNLI entailment between the retrieved (cited) context and the generated
answer. Below threshold → suppress the answer, return a refusal flagged `ungrounded`
rather than serve an unverified claim.

## 7. Harness design

- **Typed I/O end to end:** Pydantic models at every stage boundary
  (`app/models/*.py`) — no untyped dicts crossing module lines.
- **Retries:** `app/harness/retry.py` — exponential backoff with full jitter, bounded
  attempts and total time, wrapping every external call (Groq, Cerebras; Sarvam's own
  WebSocket reconnection is out of scope for this harness).
- **Circuit breaker:** `app/harness/circuit_breaker.py` — N consecutive failures opens
  the circuit and routes to failover; a half-open probe after cooldown either closes it
  or reopens and restarts the cooldown clock. Drives Groq-primary/Cerebras-failover in
  `app/generation/generator.py`.
- **Degradation ladder**, explicit and logged:
  - Sparse index search fails → dense-only (`app/retrieval/retriever.py`)
  - Grounding model raises → serve the answer flagged unverified, not blocked
  - Both LLM providers down → return retrieved passages with an honest "generation
    unavailable" outcome, never a guess
  - (ColBERT rerank is permanently absent rather than a live degradation — see §6)
- **Structured JSON logging:** every request logs id, transcript, language, outcome,
  stage timings, scores, refusal reason, and provider used, as one JSON line
  (`app/logging_setup.py` + `app/pipeline.py::_log_outcome`).
- **Deterministic replay runner:** `scripts/replay_benchmark.py` — a fixed, seeded
  query sample regenerates the entire latency table from one command.
- **Tool-calling:** retrieval is exposed as a typed callable
  (`Retriever.retrieve(query) -> RetrievalResult`), not string-concatenated into the
  generation prompt — `app/generation/prompt.py` builds structured context from the
  typed `ScoredChunk` list.

**Chaos test (kill Groq → Cerebras serves; kill both → graceful):** _pending — needs
Cerebras billing enabled first (see Limitations); the failover path itself is
unit-tested against a mock (`tests/test_circuit_breaker.py`,
`tests/test_generator.py`) and will be live-verifiable once that's unblocked._

## 8. Reproduce it yourself

All from `backend/`, with a Python 3.11 venv and `pip install -e ".[dev]"`.

```bash
# 1. Build the corpus (streams from ai4bharat/MSMARCO-XI, deterministic, seed=42)
python scripts/build_corpus.py --n-per-language 10000

# 2. Build all 5 chunking strategies' indexes (resumable per-strategy)
python scripts/build_index.py --corpus data/corpus.jsonl --output-dir data/index

# 3. Calibrate guardrail thresholds against the eval set
python scripts/calibrate_guardrails.py

# 4. Chunking comparison table (spec §14.1)
python scripts/eval_retrieval.py

# 5. Full latency benchmark, ≥500 queries, cold+warm separated (spec §13, §14)
python scripts/replay_benchmark.py --sample-size 500

# 6. Publish artifacts so a deployed backend can pull them at startup
python scripts/push_artifacts.py --create

# Test suite
pytest
```

## 9. Honest limitations

- **Embedding model is `multilingual-e5-small` (int8 ONNX), not BGE-M3.** BGE-M3 was
  the spec's default assumption under a GPU Space; this build is CPU-only (HF Spaces'
  GPU tier turned out to be paywalled — see below), and BGE-M3 on CPU blows the latency
  budget by an order of magnitude. This is the single biggest deviation from spec §4
  and the reason ColBERT rerank and the BGE-M3 sparse lexical weights are both absent
  (replaced with a from-scratch BM25 sparse index instead).
- **Backend host is Railway, not Hugging Face Spaces.** Discovered mid-build: both HF
  Spaces' persistent-process tier and its GPU tier require a paid plan. Render was the
  first pivot target; a friend's Railway Hobby plan replaced that before Render was
  ever actually deployed. The artifact-pull-at-startup pattern spec §16.2 describes
  for HF Spaces (container disk isn't durable) applies identically here and is what
  `app/artifacts.py` implements, platform-agnostic.
- **Cerebras failover is code-complete but not live-verified.** The API key
  authenticates but returns 402 Payment Required on both available models as of this
  build. The failover path itself is unit-tested against a mock; the "kill Groq, watch
  Cerebras serve" chaos test needs billing enabled first.
- **Input guardrail pattern lists (unsafe content, prompt injection) are
  English-focused.** A hand-curated list can't have broad non-English coverage by
  construction — Groq offers a hosted moderation model that would close this gap, but
  a network round-trip there would blow the ~1ms input-guardrail budget by roughly two
  orders of magnitude. Not added.
- **Grounding verification measures ~420ms** (PyTorch fp32,
  `MoritzLaurer/mDeBERTa-v3-base-mnli-xnli`) against a ~15ms target in spec §13.2 —
  the single largest budget miss after generation itself. ONNX quantization was tried
  and made it *slower* (~580ms int8, ~475ms fp32) — the opposite of what happened with
  the e5 encoder, and the opposite of what the spec's budget assumes. Reported
  honestly; `enable_grounding` stays a toggle so the cost of safety is visible rather
  than hidden (§6's ablation table).
- **Corpus is 10,000 passages/language** (140,032 total), not the spec's flat 50,000
  default — calibrated from measured local encoder throughput to keep a full 14-
  language × 5-strategy index build inside a tractable unattended window on this
  machine's hardware. Real headroom exists to raise this later.
- **STT language coverage: no gap found**, contrary to spec §9's anticipation. Sarvam's
  `saaras:v3-realtime` (verified live against docs.sarvam.ai, 2026-08-20) covers all 14
  corpus languages including Sanskrit and Odia. Worth stating as an update to the
  spec's assumption, not a silently dropped warning.
- **What breaks at scale:** the sparse (BM25) index and metadata store are
  single-process, in-memory-at-load structures — fine at this corpus size, would need
  sharding or an external store well before 10× the passage count. All 5 strategies'
  retrievers load simultaneously in the serving process's RAM (so the frontend's live
  strategy selector means something); at a larger corpus this would need to become
  load-on-demand per strategy instead.
- **What I'd do with more time:** implement true ColBERT-style late-interaction
  rerank against a multi-vector encoder (would need a model swap, not just more
  compute); widen the injection/safety pattern lists per-language rather than
  English-only; raise `passages_per_language` now that real throughput is
  established; run the full ablation grid (`enable_input`/`enable_retrieval_gate`
  cross product, not just the grounding toggle) instead of the single comparison
  in §6.

## 10. Setup instructions

**Backend** (`backend/`): Python 3.11, `pip install -e ".[dev]"`. Secrets
(`SARVAM_API_KEY`, `GROQ_API_KEY`, `CEREBRAS_API_KEY`, `HF_TOKEN`) via a `.env` file
locally (never committed — see `backend/.gitignore`) or platform env vars in
production. `uvicorn app.main:app --host 0.0.0.0 --port 7860`.

**Frontend** (`frontend/`): Node.js, `npm install`, `npm run dev`. One env var:
`NEXT_PUBLIC_API_BASE_URL` pointing at the backend's public URL.

**Deploy:** frontend auto-deploys to Vercel from pushes to `main` (root directory
`frontend/`). Backend deploys to Railway from the same repo (root directory `backend/`,
Dockerfile-based); on a cold container it pulls the corpus + built indexes from the HF
dataset repo (`RaviR2005/raingoa-artifacts` by default, overridable via
`RAINGOA_ARTIFACTS_REPO`) before marking itself ready.
